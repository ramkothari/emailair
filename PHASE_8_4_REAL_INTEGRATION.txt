PHASE 8.4 — REAL INTEGRATION ANALYSIS

Using the actual source files you provided, here are the findings and a concrete, non-code implementation plan that answers your questions 1–6.

1) Trace the complete Run Task flow (actual code call chain)

- `TaskCard` (components/TaskCard.tsx): renders a Run button and calls `onRun(task.id)` when Run is clicked.
- `SaveTaskButton` (components/SaveTaskButton.tsx): maps `onRun` to its local `handleRunTask(task)` and passes `onRun` to each `TaskCard`.
  - `handleRunTask(task)` sets `selectedTask` state and opens `runModalOpen = true` (so it controls the Run modal).
- `RunTaskModal` (components/RunTaskModal.tsx): receives `open`, `task`, `onClose`, `onExecute` props from `SaveTaskButton`.
  - When the user clicks Confirm in `RunTaskModal`, `handleConfirm()` calls `await onExecute(task.action)` and then `onClose()`.
- `SaveTaskButton.handleExecuteTask(action)` (components/SaveTaskButton.tsx): called by `RunTaskModal`'s `onExecute` prop. This runs:
  - `if (!selectedTask || !onRunTask) throw` — guard
  - `await onRunTask(selectedTask)` — this is the external entrypoint where the app integrating `SaveTaskButton` must provide `onRunTask`.

Summary: current runtime path for "Run" stops at `onRunTask(selectedTask)` provided to `SaveTaskButton`. The app-level integration must supply `onRunTask` to continue the flow.

2) Where `TaskPreviewCard` should be rendered

- `TaskPreviewCard` is the preview + confirmation + execution UI (components/TaskPreviewCard.tsx). It expects:
  - `taskName`, `action`, `emails`, `analysis`, `hasGoogleSession`, `onCancel`, `onExecuteAction`, `onExecutionSuccess`.

- The correct place to render `TaskPreviewCard` is inside the `RunTaskModal` (components/RunTaskModal.tsx) in place of (or above) the current static placeholder area that says "[Results will appear after search]" and "AI Analysis: Results will be analyzed before you confirm the final action." In other words, `RunTaskModal` should:
  - Acquire the preview result (runTaskPreview) for the `task`,
  - Render `TaskPreviewCard` populated with that preview result, and
  - Wire `TaskPreviewCard.onExecuteAction` to the existing production handlers (archive/delete/download) via `onRunTask` or a small adapter.

Why RunTaskModal: it already owns `task`, open/close lifecycle, and the existing confirm button. Replacing the single confirm flow with the preview-confirm-execute flow is minimal and matches UX: open modal → preview analysis → confirm → execute.

3) What data is missing to call `runTaskPreview()`

`runTaskPreview<TSearch>(task: TaskPreviewDefinition<TSearch>, executeSearch)` requires:
- `TaskPreviewDefinition<TSearch>` with fields: `id`, `title`, `action`, `search` (TSearch), `searchLabel?`, `maxResults?`.
- An `executeSearch` implementation: `(task) => Promise<TaskPreviewEmail[]>` which can run the search described by `task.search` and return an array of `TaskPreviewEmail` objects.

From the current `Task` shape (lib/tasks/task-types.ts) we only have:
- `id`, `name`, `query` (string), `action`, timestamps.

Missing pieces:
- A `search` payload (TSearch) inside the task. `task.query` is a freeform string — not typed `EmailFilter`.
- An `executeSearch` function that knows how to interpret `task.query` (or `task.search`) and call the Gmail preview/search handlers (server actions like `previewFilterAction` or `searchEmails`) to return `TaskPreviewEmail[]`.

So the missing data is structured search criteria (EmailFilter) or an agreed parsing strategy to convert `query` → `EmailFilter` at runtime.

4) Is `Task.query` sufficient?

- Short answer: Not reliably.

- Why: `Task.query` is an opaque saved string (e.g., "amazon"). `runTaskPreview()` expects a `TaskPreviewDefinition.search` that the `executeSearch` can use to call `searchEmails` or an appropriate search API. The codebase implements `searchEmails(accessToken, filter: EmailFilter, limit)` and `previewFilterAction(filter)` which both expect an `EmailFilter` shape (sender, subject, hasAttachment, olderThanDays), not a generic freeform string.

- Possible but fragile: If you implement an `executeSearch` that treats `task.query` as a Gmail query string (raw q= value) and you build a search function that uses the Gmail API directly with that raw query, then `Task.query` could be used as-is. However: current `lib/gmail.searchEmails` expects `EmailFilter` and internal app logic (FilterBuilder, previewFilterAction) uses `EmailFilter` objects, not raw query strings. There is no canonical parser in-code that converts `query` → `EmailFilter`.

Therefore relying only on `Task.query` is a brittle shortcut; robust integration requires storing structured search criteria.

5) Should tasks store: `EmailFilter`, `Query String`, or Both?

Recommendation: store both (backwards-compatible) — i.e., keep `query` (string) for human readability and legacy tasks, and add a new `search` property with the structured `EmailFilter` shape.

Rationale:
- Backwards compatibility: Existing tasks already have `query`. Keep it to avoid invalidating saved tasks.
- Robust execution: Structured `EmailFilter` (sender, subject, olderThanDays, hasAttachment) maps directly to `lib/gmail.searchEmails` and `app/actions/filter-actions.ts`, making preview and execution deterministic and type-safe.
- Flexibility: If the user saved a freeform query via UI (or older task), an adapter can attempt to interpret `query` at runtime (best-effort) and fall back to a raw Gmail q= search if `search` is absent.

Thus: migrate to `Task { id,name,query,action,search? }` where `search?: EmailFilter` is optional but preferred for execution.
